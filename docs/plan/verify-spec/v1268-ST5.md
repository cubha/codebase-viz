### VERIFY-SPEC — SubTask ST5 (Tab3 ERD nodemap 마커)

- 기준선 요구사항: "Tab3 hover·클릭 딥링크 전건". v62-D2(resolveBySuffix) 재설계 금지, ERD 전용 경로.
- 변경 파일: `packages/renderer/src/erd/db-diagram.ts` (+test)
- 관찰 가능한 계약: erd 경로에서 테이블 선언마다 `%% nodemap:<sanitizeId(name)>=<table IR id>`, 소스 프록시(라우트·
  컴포넌트·BE Repository) 라벨마다 대표 소스 IR id 마커. `buildDiagrams().nodeMap`에 해석되고 `dbScreen`엔 마커가 남지 않는다.
  청킹 폴백(`buildDbScreenWithFallback`)도 청크별로 같은 빌더를 불러 동일.
- 구현 결정:
  - 같은 라벨로 합쳐진 소스가 여럿이면 **첫 소스**(queries 엣지 순서)를 대표로 — 결정론만 보장.
  - flow 모드(`buildFeApiCallDiagram`)는 건드리지 않음(기존 ep_* 마커 경로).
  - 테스트 강화: 청킹 테스트가 기본 임계값에선 청킹을 안 타는 허수였음 → `nodeThreshold: 20` + 청크 수 단언 추가.
- 인접 경계: NODE_MAP은 탭 공용 네임스페이스라, 마커는 suffix 해석보다 우선한다 — Tab1/Tab2에 **같은 선언 id**가 있으면
  Tab3 마커가 덮어쓴다. 소스 라벨은 `sanitizeId(node.name)`(컴포넌트)·경로 기반(라우트)이라 Tab2의 `leaf_`·`di_` 접두사 id와는
  겹치지 않을 것으로 보지만 전수 확인은 안 함. 페어(FE+BE) 경로는 dbScreen이 emittedTexts에 포함돼 동일 적용.
- 미확인 사항: 대상 id 충돌 시 FE/BE nodeMap 병합(`mergeNodeMaps`)이 어느 쪽을 택하는지 페어 실데이터로 확인 안 함.
